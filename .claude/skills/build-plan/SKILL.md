Read first: AGENTS.md, PRE-EXISTING.md, README.md, data/README.md, package.json, everything in .claude/ (rules, skills, agents, hooks), src/agent/prompts/*.md, evals/, src/lib/ (including openapi.ts) and src/app/.

The project. Tradeflow is a Dhaka Stock Exchange portfolio ledger on synthetic data: data/*.json and data/sources/*.csv, 190 sessions from 11 Jan to Thu 1 Oct 2026, 15 symbols in 7 sectors, 45 trades. Everything at the git tag pre-hackathon is pre-existing, including announcements, dividends and bonus shares, the broker and bank files, DSEX and the sector indices, the trade journal, as-of views, attribution, the what-if preview (POST /api/what-if), reconciliation, fundamentals, the owner profile, /api/health, /api/openapi.json, docker-compose.yml, the Dockerfile and npm run db:load. The build adds only the AI layer: agents that explain, check and review, citing the query behind every number. It is a review tool, never trading advice.

Features, in priority order:
- Core. A1 Explain my week: why the portfolio moved, citing announcements, fundamentals, sector and DSEX attribution, and dividends. A2 Thesis check: each journal thesis against announcements, fundamentals and dividends: confirmed, contradicted or open. A3 Pre-trade check: before a trade is saved, an agent reasons over what_if (previewTrade, as behind POST /api/what-if), the owner's theses and past reviews; if a rule would break, it escalates to the owner (needs_human). A5 Learning from corrections: the owner's feedback is mined into H-MEM as a user_correction and recalled next time; the Meterless World Model holds holdings, announcements and facts with their sources.
- Next. A4 Reconciliation agent: explains each difference in the deterministic reconciliation, proposes a fix, and applies it only after the owner approves. Its sql() joins tradeflow_ledger and tradeflow_external through Zetaris.
- Stretch. A6 a router agent, a trace viewer and a review queue. A7 an MCP server generated from /api/openapi.json. A8 a weekly briefing: one call that chains explain_week, thesis_check and reconcile into one report.

Hard constraints:
- Zetaris does a real job: week_moves, sector_vs_stock, announcements_between, fundamentals_latest and journal_for_symbol are each one Lightning SQL statement run through its REST API as the read-only role zetaris_ro on tradeflow_ledger and tradeflow_external (made by npm run db:load), with a local fallback. dividends_between, rule_findings and reconciliation (the cross-database join) get sql() with the reconciliation agent, and run locally until then. what_if always runs locally.
- Meterless does two real jobs. First, memory: the H-MEM and World Model engines are copied or implemented from the Meterless reference (see memory.mdc). H-MEM recalls the owner's rules, theses, past reviews and corrections before each run and stores the accepted review after; H-MEM and the World Model are the build's working Meterless Engine feature, with the passing tests in src/agent/memory.test.ts, src/agent/corrections.test.ts and src/agent/world.test.ts as evidence. Second, Power: the organisers' 21 Oct guide says the app must support Meterless Nightshift as a primary AI provider, so every model call goes to the one OpenAI-compatible endpoint in METERLESS_BASE_URL (the Nightshift Console's Runtime URL), with the Nightshift Runtime token as METERLESS_API_KEY, never to a hardcoded host. The NVIDIA key is set only in Nightshift's Providers tab, never in .env, and at least one Nemotron model runs through Nightshift in a working feature.
- NVIDIA Nemotron, called only through the endpoint in METERLESS_BASE_URL (Meterless Nightshift): the "strong" model for the Planner and the Writer, "main" for the Analyst, "fast" for the Evaluator's scoring, each the exact meterless/* id that GET <METERLESS_BASE_URL>/models lists (tier ids are routing modes (meterless/deep, auto, fast); Nightshift picks the model from its active lanes (Nemotron lanes only); a concrete model id in the request does not steer the route; two tiers may hold the same id). Every request sends the headers meterless-app: tradeflow and meterless-scope: user. Model ids only in config.ts. Tool calling: the Analyst gets the task's named queries as native tools (OpenAI function calling) and may call them for evidence the plan missed, at most MAX_TOOL_ROUNDS rounds, each call through runQuery (guards.beforeQuery, the query cache and the budget); if the provider returns no tool_calls, the planned queries alone are used. Every other exchange is JSON, and the client strips reasoning blocks and code fences before parsing. If the strong model is unavailable (404, or a timeout after one retry), the call falls back to "main" and the trace says so.
- The harness, with every limit in config.ts: at most 5 planned queries, each with a one-line why written to the trace; MAX_ROUNDS 3, MAX_QUERY_CALLS 20, MAX_MODEL_CALLS 12, MAX_TOKENS_PER_RUN; QUERY_TIMEOUT_MS 20000, MODEL_TIMEOUT_MS 180000, MODEL_TIMEOUT_STRONG_MS 180000, ROUND_TIMEOUT_MS 300000, RUN_TIMEOUT_MS 600000; MAX_ROWS_PER_QUERY 50, MAX_MEMORIES 5, MAX_PROMPT_CHARS; TEMPERATURE 0.2 and MAX_COMPLETION_TOKENS for every model call. Query results are cached per run by query id and params, so a retry round reuses them. On a retry the Analyst receives its previous findings and the Evaluator's fix, and revises instead of starting again. The Evaluator checks in code before it scores: every number is in a cited row, no advice, and the review covers what mattered most (for explain_week, the holding with the largest absolute contribution). Its total out of 9 is the trace's confidence. Every reply carries usage { model_calls, query_calls, tokens_in, tokens_out, duration_ms }, the round it was accepted in and the Evaluator's scores. A spent limit or timeout returns status needs_human with the best draft, never a hang.
- Built with Claude Code, run in Orca's terminal; each step logged in BUILD-LOG.md.
- For judges: POST /run on PORT 8000 and a CLI (npm run agent), JSON in and out; the organisers recommend run.py at the root as practice, not a rule, so the README maps it to these two. The existing Dockerfile unchanged, run with -e PORT=8000, CPU only, one documented command from a clean clone. SAMPLE_MODE=true runs the real agent code on local data with no keys or network. Logs to stdout and logs/trace-<run_id>.jsonl with timestamp, run_id, agent_name, action, input_summary, output_summary, target_agent, model, confidence, retry_count and status, plus why, duration_ms and usage. At least 3 input_examples, each with an output_example generated by a real run. A README with the 8 AI-usage disclosures: models and providers, agent frameworks, partner tech and where, libraries, data sources marked synthetic, adapted open-source code, limitations, and sample-mode behaviour. A demo video of about 3:15 (the limit is 1-4 minutes). No secrets anywhere.
- Never: stored or hardcoded answers, hand-written traces, buy, sell or hold advice, data inside system prompts, re-implemented maths, or edits to pre-existing files beyond what AGENTS.md rule 1 allows.
