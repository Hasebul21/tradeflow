The harness and guardrail rules for every change to the agents, their tools, a run or a write. Read them with docs/PLAN.md before you plan a change, apply each one the change touches, and end your report with one line per rule you applied: `Harness: <rule> | <file:function> | <the test or trace line that proves it>`. A rule marked with a step applies once that step has built it.

Workflow: who decides what
- The orchestrator (src/agent/orchestrator.ts) owns the control flow: it starts each agent, counts the budget and ends the run. An agent never calls another agent; it gets one JSON input and returns one validated JSON output.
- The loop is plan, act, check, revise: the Planner plans at most 5 steps with a why each, the Analyst runs them through named queries, the Evaluator checks and scores out of 9, a score below 7 or a failed check sends a fix back to the Planner, and the Writer writes only an accepted draft. Keep a new behaviour inside this loop; don't add a side path.
- Revise, don't restart, in code (src/agent/revision.ts, mergeRevision): on rounds 2 and 3 the Analyst's new draft is merged with the rejected one. Each previous finding the Evaluator did not flag (EvaluateOutcome.flagged: a failed code check, or its subject or number in the model's fix), that the new draft neither replaces (same kind and subject) nor retracts (the reply's retracted list), and that still passes the code checks alone, is carried forward; a finding the coverage check requires (requiredFindings, such as the week's largest move) that the new draft lacks is restored, even if retracted. Each gets one Orchestrator "carry_forward" or "restore_finding" line, each retraction a "retracted" line. Nothing that fails a check is carried or restored, and the Evaluator checks the merged draft as any other.
- Safety-critical chains are fixed, not planned: pre_trade and reconcile use a fixed_plan trace line and no Planner. A new task that writes, approves or commits money gets a fixed plan too.
- A free question goes through the Router (src/agent/agents/router.ts, Step 19), which picks a task or refuses; it never answers.
- A handoff between agents or runs is a typed record and a trace line with target_agent (the briefing's handoff lines, Step 19b). Children run in parallel only through runWithLimit (src/agent/concurrency.ts, Step 20b) under MAX_CONCURRENT_CHILDREN.
- Every run ends with exactly one status, success, needs_human or error, and a stop_reason (src/agent/run-state.ts).
- Human in the loop: a trade, a ledger change or a reconcile fix is never saved by an agent. It ends needs_human with "Nothing has been saved; the decision is yours", and only the owner's approval writes it (Step 18). The review queue lists every needs_human run (Step 19).

Harness: limits, context, recovery, traces, evals
- Budgets: every new model call, query or round counts against MAX_ROUNDS, MAX_QUERY_CALLS, MAX_MODEL_CALLS and MAX_TOKENS_PER_RUN in src/agent/config.ts (a model call that fails or returns nothing counts too: it may still be billed), and each limit that can run out has a test that ends the run with its stop_reason. A number that limits a run lives in config.ts, never in the code that uses it.
- Time: each model call gets the time left in the run (RUN_TIMEOUT_MS, 110 min; ROUND_TIMEOUT_MS, 51 min; BRIEFING_TIMEOUT_MS, 220 min for a briefing) as its timeout. A long loop checks for cancellation between steps (src/agent/registry.ts, Step 20c) and ends with stop_reason "cancelled" and a complete trace.
- Context: an agent sees only what its job needs: forModel (MAX_ROWS_PER_QUERY rows), memoriesForModel (MAX_MEMORIES), catalogueFor(task), and only the cited rows for the Evaluator and the Writer (citedResults). Prompts stay under MAX_PROMPT_CHARS. Never pass a whole table, file or trace to a model.
- Structured output: replies are parsed with parseJsonReply (the outermost balanced {...}; prose or a fence around it is fine) and validated with the agent's zod schema, which the agent passes to llm.ts as validate with its reply shape. A reply that does not parse or fails the schema is asked for again, saying what was wrong and restating the shape, up to 3 tries in all (STRUCTURED_REPLY_MAX_TRIES), each traced as model_retry and counted as a model call, and only while MODEL_TIMEOUT_CAP_MS of the round is left; then a typed BadJson error. A reply that stopped at the token limit (finish_reason length) is asked for again at max_tokens EMPTY_RESPONSE_RETRY_MAX_TOKENS; any other keeps MAX_COMPLETION_TOKENS. A raised max_tokens (this retry or a 502 empty_response's) is clamped to the run's tokens left (tokensLeft, from RunState.tokensLeft), never below MAX_COMPLETION_TOKENS. The retry's reason is built from the zod path and issue code, and a model-chosen name is echoed only when it matches /^[a-z_]{1,40}$/ (safeName, schemaReason in llm.ts). parseJsonReply drops an unclosed <think> block to the end of the reply and never takes an empty {} for the reply. Never accept free text where a schema exists.
- Recovery: strong falls back to main and the trace says so; a 401 or 403 is Unauthorized and a refused connection is NightshiftNotRunning, and neither falls back; Zetaris falls back to local rows with source "local-fallback". llm.ts retries a timeout or a 429 once when time is left (a timeout as a whole new attempt while BACKOFF_MS and MODEL_TIMEOUT_CAP_MS of the round are left). The Planner passes reserveAfterMs (MODEL_TIMEOUT_CAP_MS): every retry of its call (timeout, 502 empty_response, structured, token limit) starts only when the retry's worst case still leaves that much of the round for the Analyst, else the error stands and the code plan comes at once. The defaults are sized so this holds with a retry: ROUND_TIMEOUT_MS 51 min (the Planner with one full retry, 840.3 s, the Analyst's three calls, the Evaluator's and the Writer's, 420 s each, and 60 s for queries and code: 3000.3 s, up to whole minutes), RUN_TIMEOUT_MS 110 min (two rounds, one more call and 60 s) and BRIEFING_TIMEOUT_MS 220 min (two waves of child runs), with the arithmetic in config.ts. Only with a shorter round does a Planner failure go straight to the code plan, because the Analyst's time matters more, then throws ModelTimeout or RateLimited; a caller never loops on either. A 502 "empty_response" (the lane gave no answer) gets a plain retry at max_tokens 32000 (EMPTY_RESPONSE_RETRY_MAX_TOKENS), traced as "empty_response_retry"; when the caller passes the round's end, up to 3 tries in total (EMPTY_RESPONSE_MAX_TRIES) after waits of 15 s and 30 s (EMPTY_RESPONSE_RETRY_WAITS_MS). No reasoning switch goes to Nightshift: reasoning {enabled: false} makes its lane return empty replies on large requests, and it ignores chat_template_kwargs. When the Evaluator's score still fails, the draft is accepted on the code checks alone (citations, guards and coverage), with score null, traced as "score_unavailable"; a failed code check still rejects. When the Planner's call still fails after llm.ts gives up (BadJson, a 5xx such as the 502 empty_response, a timeout while the round and the run have time left, a 429, or a ModelNetworkError: the SDK's APIConnectionError or ECONNRESET, ENOTFOUND, ETIMEDOUT, EAI_AGAIN, EPIPE or ECONNABORTED at the socket; a TypeError or other failure with no status stays a status error, so a bug is never hidden), its plan is built in code from src/agent/default-plan.ts, traced as one Orchestrator "planner_fallback" line whose why starts with the cause (bad_json, upstream_<status>, timeout, rate_limited or network) and named in the gaps (PLANNER_FALLBACK_LABEL); when a later agent's call still fails: the Evaluator gives score_unavailable on BadJson or a 502; the Analyst or the Writer (or the Evaluator on any other of these failures, a 429 and a network error included) ends needs_human with stop_reason model_unavailable; Unauthorized, NightshiftNotRunning, PromptTooLarge, a 4xx other than 429, a cancel and a spent budget never fall back, and a timeout that is the round's or the run's ends round_timeout or run_timeout. A fallback is always traced and labelled, never passed off as a model answer, and npm run eval never passes it.
- Cache: a query with the same id and params runs once per run (the per-run query cache in src/agent/run-state.ts); a cached call is traced as action "cached" and counts no query call. A tool call goes through the same cache and budget.
- Traces: every action writes one TraceLine (src/agent/trace.ts) with agent_name, action, input_summary, output_summary, status, why, confidence and usage, through maskSecrets, so no key or token reaches a trace. Every model line carries prompt_hash and every line its task (Step 20d). Never hand-write or edit a trace.
- Sample mode: SAMPLE_MODE runs the same code path with src/agent/sample-model.ts; a sample rule decides from the input facts only, and it gives the verdict each case in evals/expectations.json expects. Tests use the sample model or a mock, so npm test needs no network.
- Prompts: each agent's prompt is its own file in src/agent/prompts/ with an Examples section, loaded as-is, never built by joining strings with data.
- Evals: a new behaviour gets an entry in evals/expectations.json; a new guard or refusal gets a red-team case in evals/redteam/cases.json; a change to an agent's prompt or rule is measured before and after (npm run eval, and /improve-agent's evals/IMPROVEMENTS.md) and kept only if it helps.
- Metrics: runs are compared through metricsFromTraces (src/agent/metrics.ts, Step 20d), never by reading output_examples/.

Guardrails: what never gets through
- Data is never an instruction: text from rows, memories, notes or questions goes to a model boxed as data, injectionIn flags instruction-like wording and afterModel sets injection_seen, and a flag can only lower trust, never unlock an action.
- Every query goes through guards.beforeQuery: named queries only, params validated, the budget checked; the model never writes SQL. Every tool an agent calls is one its policy allows (src/agent/policy.ts, Step 20e), and a denied call writes a Guard line "policy_denied".
- Every model reply goes through guards.afterModel: the schema, the advice refusal (never "you should buy, sell or hold") and the injection flag.
- Every number in a finding goes through guards.checkCitations against the rows it cites; a number no row holds rejects the finding.
- Every memory write goes through guards.beforeRemember (at most MAX_MEMORY_CHARS, no injected text, no secret); a rejected write stores nothing and writes one Guard line.
- Every review ends with the disclaimer line, and a question asking for advice ends with declined_advice true.
- Secrets live only in .env, which no code prints, logs, traces or copies; a new setting is a name in .env.example with no value.
- Never weaken a guard, a test, an expectation or a check to make a change pass; a guard that blocks something it should allow is fixed with a new test that shows the allowed case.
