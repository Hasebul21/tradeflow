- Agents never write SQL. They pick a named query from the registry in queries.ts; code fills its parameters after guards.beforeQuery has validated them.
- The named queries are week_moves, sector_vs_stock, announcements_between, fundamentals_latest, dividends_between, journal_for_symbol, rule_findings, what_if and reconciliation. Each local() calls the src/lib function behind the matching base API (see AGENTS.md); never re-implement it. week_moves adds a first row with symbol "PORTFOLIO" from the attribution's totals (changePct, indexChangePct, differencePts), so the headline move can be cited. Each query's description is written for the Planner: what question it answers and when to use it.
- Every query call writes one trace line as agent "Query": the query id, params, source and, for Zetaris, the start of the SQL in input_summary; the row count in output_summary; duration_ms. Results are cached per run by query id and params.
- Named queries get sql(): one Lightning SQL statement returning only the columns it can compute (week_moves: symbol, from_close, to_close, change_pct); local() adds the PORTFOLIO row and the label in code, and parity compares only the SQL's columns. week_moves, sector_vs_stock, announcements_between, fundamentals_latest and journal_for_symbol first; dividends_between, rule_findings and reconciliation with the reconciliation agent, running locally (source "local") until then. npm run parity proves each one. what_if is a calculation on a trade that hasn't happened, so it always runs locally and the trace says so.
- The data lives in two databases made by the pre-existing npm run db:load: tradeflow_ledger (instruments, bars, transactions, contributions, rule_settings, sector_targets, trade_plans, corporate_actions, index_bars, sector_index_bars, journal, profile) and tradeflow_external (broker_statement, bank_deposits, announcements, fundamentals). Column names match the JSON and CSV fields. Never change scripts/load-postgres.mjs or scripts/db-schema.mjs.
- Each database is a Zetaris datasource of the same name. reconciliation's sql() joins tradeflow_ledger and tradeflow_external in one statement, with the same price tolerance as PRICE_TOLERANCE_BDT in src/lib/reconcile.ts.
- Lightning SQL rules (zetaris/getting-started AGENTS.md): one statement per call, no trailing semicolon, qualified names as listed by SHOW DATASOURCE TABLES, aggregate in SQL so only small results come back. Lightning SQL runs on Spark SQL: use Spark date and cast functions, never Postgres-only syntax; zetaris/getting-started's docs/guides/zetaris-lightning-sql-companion.md (read it with curl) lists confirmed limits.
- Zetaris REST may return values as strings (check this on the first real call). Convert numbers explicitly; treat values such as 0E-18 as 0.
- The Zetaris client sends Authorization: Bearer, X-Org-ID and a fresh UUID X-Request-ID, with a 20 s timeout (QUERY_TIMEOUT_MS). A timeout gets one retry; then, or on any error, fall back to local(), mark the result source "local-fallback" and trace status "fallback". No rows is rows: [], never an error.
- Zetaris connects as zetaris_ro, which may only SELECT. Never put a password in SQL that is committed; use the Zetaris GUI for CREATE DATASOURCE.
